ABSTRACT
================================================================================

The rapid growth of digital information across organizations has created an urgent need for systems that can intelligently store, retrieve, and reason over large volumes of unstructured documents. Traditional keyword-based search systems often fail to capture the semantic meaning of user queries, returning irrelevant results or requiring users to know the exact wording of the information they seek. This project presents the design and implementation of an AI-powered knowledge base system that uses Retrieval-Augmented Generation (RAG), a technique that combines semantic document retrieval with Large Language Model (LLM) reasoning, to enable users to upload documents in multiple formats and receive accurate, context-aware answers to natural language questions, complete with source attribution. The system was implemented as a RESTful API using the FastAPI web framework, with OpenAI's GPT models for language generation and embedding, ChromaDB as a vector database for semantic search, MySQL for relational data storage, and the Unstructured library for multi-format document parsing. The document ingestion pipeline partitions uploaded files into text, tables, and images, enriches visual content using OpenAI's vision capabilities, chunks the content into semantically meaningful segments, generates vector embeddings, and stores them for retrieval. When a user asks a question, the system retrieves the most relevant document chunks via cosine similarity search, constructs a context-aware prompt, and generates an answer grounded strictly in the retrieved content, preventing hallucination. The system also supports multi-turn conversations, user authentication with JWT tokens, embedding caching for cost optimization, and per-message cost tracking. Testing was carried out through unit testing, integration testing, and system testing to verify correctness across all components. Results demonstrated that the RAG-based system consistently returned accurate, source-attributed answers, significantly outperforming traditional keyword search in both relevance and user satisfaction. The study concludes that Retrieval-Augmented Generation is a practical and effective approach for building intelligent knowledge management systems and recommends further exploration of open-source LLMs and real-time document streaming for future enhancements.

Keywords: Retrieval-Augmented Generation, Knowledge Base, Large Language Model, Natural Language Processing, Semantic Search, Vector Database, API Development.

CHAPTER ONE
INTRODUCTION
================================================================================

1.1 Background of the Study

The volume of digital information generated by organizations worldwide continues to grow at an extraordinary pace. According to Statista (2024), the total volume of data created, captured, copied, and consumed globally reached approximately 147 zettabytes in 2024, with projections indicating continued exponential growth. Within organizations, much of this information exists as unstructured data -- documents, reports, manuals, emails, and knowledge articles -- that is difficult to search, organize, and reason over using traditional database systems.

Knowledge management systems have long served as tools for capturing, organizing, and sharing institutional knowledge. Early systems relied on manual categorization and keyword-based search, which required users to know the exact terms present in the documents they sought. While effective for structured queries, keyword search struggles with natural language questions, synonyms, and conceptual queries where the user's intent does not match the literal wording of stored documents.

The emergence of Large Language Models (LLMs) such as OpenAI's GPT-4 (OpenAI, 2023) and Google's Gemini (Google DeepMind, 2024) has transformed the landscape of natural language understanding. These models, trained on vast corpora of text, can generate coherent, contextually appropriate responses to a wide range of questions. However, LLMs have a well-documented limitation: they can produce plausible-sounding but factually incorrect responses, a phenomenon commonly known as "hallucination" (Huang et al., 2023). When used for knowledge management, this limitation is particularly problematic, as users need verifiable, accurate answers grounded in their organization's actual documents.

Retrieval-Augmented Generation (RAG), first introduced by Lewis et al. (2020) at Facebook AI Research, addresses this limitation by combining the generative power of LLMs with an external retrieval mechanism. In a RAG system, when a user asks a question, the system first retrieves the most relevant passages from a document store using semantic similarity search, then provides these passages as context to the LLM, which generates an answer grounded in the retrieved content rather than relying solely on its parametric knowledge. This approach significantly reduces hallucination while enabling the system to answer questions about private, domain-specific, or recently created documents that were not part of the LLM's training data.

This project addresses the practical challenge of building such a system by designing and implementing an AI-powered knowledge base API that uses the RAG approach, enabling users to upload documents in multiple formats, ask natural language questions, and receive accurate, source-attributed answers.


1.2 Statement of the Problem

Organizations across industries accumulate large volumes of documents -- policy manuals, technical reports, meeting minutes, research papers, and operational guides -- that contain valuable institutional knowledge. Accessing specific information within these documents remains a significant challenge for several reasons.

First, traditional keyword-based search systems require users to know the exact terminology used in the documents, which is often impractical when the information spans multiple domains or uses varied language. Second, even when documents are found, users must manually read through lengthy texts to locate the specific answer to their question, which is time-consuming and error-prone. Third, standalone Large Language Models, while capable of generating helpful responses, cannot reliably answer questions about private organizational documents because they lack access to this information and may fabricate responses that sound plausible but are incorrect.

There is, therefore, a need for an intelligent knowledge base system that can accept documents in various formats, understand their content semantically, retrieve the most relevant passages in response to natural language questions, and generate accurate answers grounded strictly in the retrieved content, with clear attribution to the source documents.


1.3 Aim and Objectives of the Study

The aim of this study is to design and implement an AI-powered knowledge base system using Retrieval-Augmented Generation (RAG) that enables intelligent, context-aware question answering over uploaded documents.

The specific objectives of the study are to:

1. Design and implement a document ingestion pipeline capable of processing multiple document formats (PDF, DOCX, TXT, Markdown, HTML, and JSON), including extraction and enrichment of text, tables, and images.

2. Design and implement a semantic search system using vector embeddings and a vector database to retrieve document passages relevant to user queries.

3. Integrate a Large Language Model (LLM) to generate accurate, context-grounded answers from retrieved document passages, with source attribution.

4. Develop a RESTful API with user authentication, multi-turn conversation support, and cost tracking, using modern web framework practices.

5. Evaluate the accuracy and relevance of the RAG-based question answering system compared to traditional keyword-based search.


1.4 Significance of the Study

This study is significant in several respects. Academically, it contributes to the growing body of knowledge on the practical application of Retrieval-Augmented Generation in software systems, providing a documented, replicable methodology that future students and researchers can build upon. Practically, it demonstrates a working system architecture that organizations, developers, and small businesses can adopt to build intelligent knowledge management tools without requiring extensive machine learning expertise, since the system leverages existing LLM APIs and open-source vector databases. The study also contributes a concrete implementation of cost-optimized RAG, including embedding caching and token tracking, which addresses a common concern in deploying LLM-powered applications. Finally, the project serves as a foundation for further research into advanced RAG techniques such as hybrid retrieval, agentic RAG, and multi-modal knowledge bases.


1.5 Scope of the Study

This study covers the design, implementation, and evaluation of a complete RAG-based knowledge base system exposed as a RESTful API. The scope includes:

- A document ingestion pipeline supporting six file formats (PDF, DOCX, TXT, Markdown, HTML, JSON) with text extraction, table summarization, image description, semantic chunking, and vector embedding.
- A semantic retrieval system using ChromaDB as the vector database and OpenAI's text-embedding-3-small model for generating embeddings.
- An answer generation system using OpenAI's GPT models, constrained to generate responses only from retrieved context.
- A RESTful API built with FastAPI, including endpoints for document management, chat-based querying, and user authentication.
- User authentication using JSON Web Tokens (JWT) with refresh token support.
- Multi-turn conversation management with chat history and session tracking.
- Embedding caching and per-message cost tracking.

The study does not extend to building a graphical user interface (frontend), deploying the system to a cloud production environment, implementing real-time document streaming or web scraping, or supporting languages other than English. The system is developed and tested on a local development environment.


1.6 Limitations of the Study

The study is constrained by the cost associated with using commercial LLM APIs (OpenAI), which limited the volume of testing and training that could be conducted. The reliance on a third-party API also means the system's answer quality is dependent on the capabilities and availability of the external LLM provider. Additionally, the system's retrieval accuracy is influenced by the quality of the chunking strategy and embedding model, which may not perform optimally for all document types, particularly those with highly technical or domain-specific language. Time constraints associated with the academic calendar also limited the number of document formats tested and the scale of the evaluation dataset.


1.7 Definition of Terms

- Retrieval-Augmented Generation (RAG): A technique that enhances the output of a Large Language Model by first retrieving relevant information from an external knowledge source and providing it as context for generation.

- Large Language Model (LLM): A deep learning model trained on large amounts of text data that can understand and generate human language. Examples include GPT-4, Gemini, and LLaMA.

- Vector Embedding: A numerical representation of text (typically a high-dimensional vector) that captures its semantic meaning, enabling mathematical comparison of textual similarity.

- Vector Database: A specialized database optimized for storing and querying vector embeddings using similarity search algorithms such as cosine similarity or approximate nearest neighbours.

- Semantic Search: A search approach that understands the meaning and intent behind a query, rather than matching exact keywords.

- Chunking: The process of dividing a large document into smaller, semantically meaningful segments (chunks) suitable for embedding and retrieval.

- API (Application Programming Interface): A set of defined rules and protocols that allows different software applications to communicate with each other.

- RESTful API: An API that follows the Representational State Transfer (REST) architectural style, using standard HTTP methods for communication.

- Hallucination: In the context of LLMs, the generation of plausible-sounding but factually incorrect or fabricated information.

- Token: The basic unit of text processed by an LLM. A token can be a word, part of a word, or a punctuation mark.

- Cosine Similarity: A mathematical measure that calculates the cosine of the angle between two vectors, used to determine how similar two pieces of text are based on their embeddings.

- JWT (JSON Web Token): A compact, URL-safe token format used for securely transmitting information between parties, commonly used for authentication.

CHAPTER TWO
LITERATURE REVIEW
================================================================================

2.1 Introduction

This chapter reviews existing literature relevant to the study under three broad sub-headings: the conceptual framework, which clarifies key concepts underpinning the study; the theoretical framework, which discusses the underlying natural language processing and information retrieval theories; and the review of related works, which examines previous studies and systems relevant to intelligent knowledge base design using AI techniques.


2.2 Conceptual Framework

2.2.1 Concept of Knowledge Management Systems

Knowledge Management Systems (KMS) are information systems designed to support the creation, capture, storage, retrieval, and dissemination of knowledge within an organization (Alavi & Leidner, 2001). Traditional KMS rely on structured databases, taxonomies, and keyword search to help users locate information. While these systems are effective when the user knows precisely what they are looking for and can formulate appropriate keyword queries, they struggle with the ambiguity and variability inherent in natural language. For example, a user searching for "how to handle employee grievances" may not find a document titled "Staff Complaint Resolution Procedure" using keyword matching alone, even though both phrases refer to the same concept.


2.2.2 Concept of Natural Language Processing

Natural Language Processing (NLP) is a branch of artificial intelligence concerned with enabling computers to understand, interpret, and generate human language (Jurafsky & Martin, 2024). NLP encompasses a wide range of tasks including text classification, named entity recognition, sentiment analysis, machine translation, and question answering. Modern NLP is dominated by transformer-based models, a neural network architecture introduced by Vaswani et al. (2017) in their seminal paper "Attention Is All You Need." The transformer architecture, which uses self-attention mechanisms to process input sequences in parallel rather than sequentially, forms the foundation of all major Large Language Models in use today.


2.2.3 Concept of Large Language Models

Large Language Models (LLMs) are deep neural networks, typically based on the transformer architecture, that have been trained on vast corpora of text data to predict the next token in a sequence. Through this training process, LLMs develop a broad understanding of language, facts, reasoning patterns, and even some degree of common sense (Brown et al., 2020). Notable LLMs include OpenAI's GPT series (Radford et al., 2019; OpenAI, 2023), Google's PaLM and Gemini (Anil et al., 2023; Google DeepMind, 2024), Meta's LLaMA series (Touvron et al., 2023), and Anthropic's Claude (Anthropic, 2024).

While LLMs are remarkably capable, they have a critical limitation for knowledge management applications: they cannot reliably access or reason over information that was not present in their training data, and they may generate confident but incorrect answers when asked about unfamiliar topics (Huang et al., 2023). This limitation motivates the use of Retrieval-Augmented Generation.


2.2.4 Concept of Retrieval-Augmented Generation (RAG)

Retrieval-Augmented Generation (RAG) is a paradigm that enhances the factual accuracy and domain-specificity of LLM outputs by combining them with an external retrieval system. The concept was formalized by Lewis et al. (2020), who demonstrated that augmenting a seq2seq generative model with a retrieval mechanism over a non-parametric knowledge base significantly improved performance on knowledge-intensive NLP tasks.

In a typical RAG pipeline, user queries are first converted into vector embeddings, which are then used to search a vector database containing embedded document chunks. The most similar chunks are retrieved and provided as context within the LLM's prompt, along with the user's original question. The LLM then generates a response grounded in this retrieved context, rather than relying solely on information stored in its parameters. This approach offers several advantages: it reduces hallucination, allows the system to answer questions about private or recent documents not seen during LLM training, and provides traceable source attribution for generated answers.


2.2.5 Concept of Vector Databases and Semantic Search

Vector databases are purpose-built database systems optimized for storing, indexing, and querying high-dimensional vector embeddings (Pan et al., 2024). Unlike traditional relational databases that match exact values or patterns, vector databases use similarity metrics such as cosine similarity, Euclidean distance, or dot product to find vectors that are mathematically closest to a query vector. Popular vector databases include ChromaDB, Pinecone, Weaviate, Milvus, and Qdrant. Semantic search, powered by vector embeddings, enables retrieval based on the meaning of text rather than literal keyword overlap. For example, a query about "employee vacation policy" can semantically match a document chunk discussing "staff annual leave entitlements," even though the two texts share few common keywords.


2.3 Theoretical Framework

2.3.1 Information Retrieval Theory

Information Retrieval (IR) theory provides the foundational principles for how documents are indexed, searched, and ranked in response to user queries (Manning et al., 2008). Classical IR models include the Boolean model, the Vector Space Model (Salton et al., 1975), and probabilistic models such as BM25 (Robertson & Zaragoza, 2009). The Vector Space Model, which represents both documents and queries as vectors in a high-dimensional term space and ranks documents by cosine similarity to the query vector, is conceptually the closest predecessor to modern dense retrieval using neural embeddings. The key advancement of dense retrieval, as used in this project, is that the vectors are generated by neural networks (embedding models) that capture semantic meaning, rather than being based on term frequency statistics alone.

2.3.2 Transformer Architecture and Attention Mechanism

The transformer architecture (Vaswani et al., 2017) underpins both the embedding models and the generative LLMs used in this project. The core innovation of the transformer is the self-attention mechanism, which allows the model to weigh the relevance of every token in an input sequence relative to every other token, enabling it to capture long-range dependencies and contextual relationships in text. This architecture replaced earlier recurrent and convolutional approaches for most NLP tasks due to its superior performance and parallelizability.

2.3.3 Embedding Models and Dense Retrieval

Dense retrieval uses neural network-based embedding models to map text passages and queries into a shared vector space, where semantically similar texts are located close together (Karpukhin et al., 2020). OpenAI's text-embedding-3-small model, used in this project, produces 1536-dimensional vectors that capture the semantic content of input text. At query time, the user's question is embedded using the same model, and the nearest document chunk vectors are retrieved using cosine similarity search. This approach significantly outperforms traditional sparse retrieval (e.g., TF-IDF, BM25) on tasks requiring semantic understanding (Thakur et al., 2021).


2.4 Review of Related Works

Several researchers and organizations have explored the application of RAG techniques to knowledge management and question answering systems.

Lewis et al. (2020) introduced the RAG framework at Facebook AI Research, demonstrating that combining a pre-trained seq2seq model with a dense retrieval component over Wikipedia significantly improved performance on open-domain question answering benchmarks. Their work established the theoretical and practical foundation for all subsequent RAG systems, including the one developed in this project.

Gao et al. (2024), in their comprehensive survey paper "Retrieval-Augmented Generation for Large Language Models: A Survey," categorized RAG approaches into Naive RAG, Advanced RAG, and Modular RAG, detailing the evolution of techniques from simple retrieve-then-generate pipelines to sophisticated systems with query rewriting, re-ranking, and iterative retrieval. The system developed in this project implements what Gao et al. classify as an Advanced RAG system, incorporating structured chunking, multi-modal content enrichment, and context-grounded generation.

LangChain, an open-source framework developed by Harrison Chase (2022), provides modular components for building LLM-powered applications, including document loaders, text splitters, embedding interfaces, vector store integrations, and chain-based prompt management. This project uses LangChain as a key orchestration layer for its RAG pipeline, leveraging its text splitting and vector store integration capabilities.

Chroma (Trychroma, 2023) is an open-source embedding database designed specifically for AI applications. It provides a simple API for storing and querying document embeddings, with support for metadata filtering and persistence. This project uses ChromaDB as its primary vector store due to its lightweight footprint, ease of integration with LangChain, and suitability for academic and small-scale deployments.

The Unstructured library (Unstructured.io, 2023) provides tools for extracting structured content from unstructured documents, supporting formats including PDF, DOCX, HTML, and images with OCR capabilities. This project uses the Unstructured library to partition uploaded documents into text elements, tables, and images, enabling comprehensive content extraction that goes beyond plain text parsing.


2.5 The Knowledge Management Industry and AI Adoption

The global knowledge management market has experienced significant growth, driven by the increasing recognition that organizational knowledge is a strategic asset. According to Grand View Research (2024), the global knowledge management market was valued at approximately USD 36.4 billion in 2023 and is projected to grow at a compound annual growth rate (CAGR) of 18.2% from 2024 to 2030, driven in large part by the adoption of AI and machine learning technologies.

Major technology companies have integrated RAG capabilities into their enterprise products. Microsoft's Copilot (2024) uses RAG to ground LLM responses in enterprise data stored in Microsoft 365 applications. Google's Vertex AI Search (2024) provides RAG-as-a-service for enterprise customers. Amazon's Bedrock Knowledge Bases (2024) offers managed RAG infrastructure on AWS. These developments indicate strong industry validation of the RAG approach that this project implements at a smaller, academic scale.

Despite these enterprise offerings, many small and medium organizations, as well as student developers, face barriers to adopting RAG technology due to the perceived complexity of the pipeline (document processing, embedding, vector storage, LLM integration) and the cost of commercial platforms. This project demonstrates that a functional RAG system can be built using freely available open-source tools and affordable API services.


2.6 Gap in Literature

While extensive literature exists on the theoretical foundations of RAG and on large-scale commercial implementations by well-resourced technology companies, there is comparatively limited published work documenting a complete, end-to-end implementation of a RAG-based knowledge base system -- from document ingestion with multi-modal content enrichment, through semantic retrieval and context-grounded generation, to API design with authentication and cost tracking -- at a scale suitable for adoption by students, small developers, and organizations with modest computing resources. Most existing tutorials and guides focus on simplified "hello world" RAG implementations that omit critical production concerns such as multi-format document support, image and table handling, embedding caching, conversation history management, and cost optimization. This study addresses that gap by implementing and documenting a complete, production-oriented RAG system within an academic project setting.

CHAPTER THREE
SYSTEM ANALYSIS AND METHODOLOGY
================================================================================

3.1 Introduction

This chapter presents the methodology adopted for the design and implementation of the AI-powered knowledge base system, an analysis of the existing (keyword-based) approach to document search, the proposed RAG-based system, system requirements, architecture, and the detailed design of the RAG pipeline that powers the system's question answering capability.


3.2 System Development Methodology

The Agile methodology was adopted for this project due to its iterative nature, which is well suited to a project involving experimental AI components whose performance can only be fully assessed after implementation and testing. The project was broken into iterative sprints covering: (1) document ingestion pipeline development, (2) vector storage and retrieval implementation, (3) LLM integration and answer generation, (4) API endpoint development, (5) authentication system implementation, (6) testing and evaluation. Feedback from each sprint, particularly regarding chunking strategies, prompt engineering, and retrieval parameters, informed refinements in subsequent sprints.


3.3 Analysis of the Existing System

Existing document search systems in most organizations rely on one or more of the following approaches:

- Keyword-based search: Systems such as Elasticsearch or basic SQL LIKE queries match user search terms against document text. This approach is fast and well-understood but fails when the user's terminology does not match the document's wording. It also cannot answer questions; it can only return documents that the user must then read manually.

- Manual categorization and tagging: Documents are organized into folders or tagged with metadata by human operators. This approach requires significant manual effort to maintain and does not scale well as document volumes grow.

- Static FAQ systems: Pre-written question-answer pairs are maintained manually. These systems can only answer questions that have been anticipated and written in advance, and they require ongoing manual updates.

These existing approaches share common weaknesses: they cannot understand the semantic intent behind user queries, they require users to know what terms to search for, they cannot synthesize information from multiple document passages into a coherent answer, and they provide no mechanism for natural language interaction.


3.4 Analysis of the Proposed System

The proposed system replaces keyword-based search with a RAG-powered knowledge base that operates in two main phases:

Document Ingestion Phase: When a user uploads a document, the system automatically partitions it into text, tables, and images using the Unstructured library; enriches visual content (images and tables) with AI-generated descriptions using OpenAI's vision capabilities; splits the enriched content into semantically meaningful chunks using a recursive character text splitter with configurable chunk size and overlap; generates vector embeddings for each chunk using OpenAI's embedding model; and stores the embeddings in ChromaDB while persisting document metadata and chunk records in MySQL.

Query and Response Phase: When a user asks a question, the system embeds the query using the same embedding model; performs a cosine similarity search in ChromaDB to retrieve the most relevant document chunks; constructs a prompt containing the retrieved context and the user's question, along with conversation history for multi-turn support; sends the prompt to OpenAI's GPT model with explicit instructions to answer only from the provided context; and returns the generated answer along with source attribution, relevance scores, and cost information.

This design ensures that answers are always grounded in the organization's actual documents, preventing hallucination, while supporting natural language interaction that does not require users to know specific keywords.


3.5 System Requirements

3.5.1 Hardware Requirements

- A personal computer with a minimum of Intel Core i5 processor (or equivalent) and 8GB RAM (16GB recommended for processing large documents).
- At least 5GB of free disk space for the application, uploaded documents, vector database, and dependencies.
- A stable internet connection for API communication with OpenAI services.

3.5.2 Software Requirements

- Python 3.12 or later as the primary programming language and runtime environment.
- FastAPI as the web framework for building the RESTful API.
- MySQL 8.0 or later as the relational database for storing document metadata, user accounts, chat sessions, and embedding cache.
- ChromaDB as the vector database for storing and querying document embeddings.
- OpenAI API access for text embedding (text-embedding-3-small) and language generation (GPT models).
- LangChain as the orchestration framework for the RAG pipeline.
- The Unstructured library for multi-format document parsing.
- Docker (optional) for containerized deployment.


3.6 System Architecture

The system architecture follows a layered design consisting of four main layers:

1. API Layer (FastAPI): Handles HTTP requests and responses, input validation, authentication, and routing. This layer exposes RESTful endpoints for document management, chat-based querying, and user authentication. It uses Pydantic schemas for request/response validation and FastAPI's dependency injection for database sessions and authentication.

2. Service Layer (Business Logic): Contains the core business logic for document processing, chat management, and user authentication. This layer orchestrates the interaction between the API layer, the RAG pipeline, and the database layer. Key services include the DocumentService (handles document upload, retrieval, and deletion), ChatService (manages chat sessions, message history, and answer generation), and AuthService (handles user registration, login, and token management).

3. RAG Pipeline Layer (AI Processing): Implements the complete Retrieval-Augmented Generation pipeline, including document partitioning, content enrichment, chunking, embedding generation, vector storage, semantic retrieval, context building, and answer generation. This layer interfaces with external AI services (OpenAI API) and the vector database (ChromaDB).

4. Data Layer (Persistence): Manages data storage across two systems: MySQL (via SQLAlchemy ORM) for structured relational data (users, documents, chunks, chat sessions, messages, embedding cache), and ChromaDB for vector embeddings used in semantic search. The dual-storage design allows the system to leverage the strengths of both relational and vector databases.


3.7 RAG Pipeline Design

3.7.1 Document Ingestion Pipeline

The document ingestion pipeline processes uploaded files through five sequential stages:

Stage 1 - Partitioning: The Unstructured library's partition function is used with a high-resolution (HI_RES) strategy to extract structured elements from the uploaded document. The output is separated into three categories: text elements (paragraphs, headings, list items), tables (tabular data), and images (embedded graphics, charts, diagrams). Each element retains metadata including its position within the document.

Stage 2 - Content Enrichment: Tables are summarized using the LLM to produce concise natural language descriptions that capture their key data points. Images are analyzed using OpenAI's vision-capable model to generate textual descriptions of their content, including chart data, diagram labels, and any visible text. This enrichment step ensures that visual content, which cannot be directly embedded as vectors, becomes searchable through its textual description.

Stage 3 - Chunking: The enriched text content is split into chunks using LangChain's RecursiveCharacterTextSplitter with a configurable chunk size (default: 1000 characters) and overlap (default: 200 characters). The overlap ensures that information spanning chunk boundaries is not lost. The recursive splitter attempts to split on natural boundaries (paragraphs, sentences, words) before resorting to character-level splitting.

Stage 4 - Embedding: Each chunk is converted into a 1536-dimensional vector embedding using OpenAI's text-embedding-3-small model. An embedding cache (stored in MySQL, keyed by the SHA-256 hash of the chunk text) is checked before making API calls, avoiding redundant embedding requests for identical text and reducing API costs.

Stage 5 - Storage: The generated embeddings, along with the chunk text and metadata (document ID, filename, upload date, file type, tags, chunk index), are stored in ChromaDB. Simultaneously, chunk records are persisted in MySQL with references to their ChromaDB vector IDs, enabling the system to enrich retrieval results with relational data.


3.7.2 Query and Retrieval Pipeline

When a user submits a question, the system executes the following steps:

Step 1 - Query Embedding: The user's question is embedded using the same OpenAI embedding model used during ingestion, ensuring that queries and document chunks exist in the same vector space.

Step 2 - Similarity Search: ChromaDB performs a cosine similarity search to find the k most similar document chunks (default k=10). If the user has specified particular document IDs to scope the search, a metadata filter is applied to restrict results to chunks from those documents.

Step 3 - Result Enrichment: The retrieved chunks are enriched with additional metadata from MySQL, including document titles, filenames, and chunk positions, providing context for source attribution.

Step 4 - Context Building: The retrieved chunks are formatted into a structured context string, with each chunk prefixed by its source document information. This context is inserted into a carefully engineered prompt template that instructs the LLM to answer the question using only the provided context.

Step 5 - Answer Generation: The prompt, including the context, the user's question, and the last 10 messages of conversation history (for multi-turn support), is sent to OpenAI's GPT model. The model generates a response grounded in the retrieved context. The system prompt explicitly instructs the LLM to state "I don't have enough information to answer this question" if the context does not contain relevant information, rather than fabricating an answer.

Step 6 - Response Packaging: The generated answer is returned along with source attribution (which documents and chunks were used), relevance scores (cosine similarity converted to a 0-100 scale), and token/cost information.


3.7.3 Reward Design: Relevance Scoring

The system calculates a relevance score for each retrieved chunk by converting the cosine similarity distance returned by ChromaDB into a percentage score on a 0-100 scale. This score provides users with a transparent indication of how closely each source passage matches their question, enabling them to assess the reliability of the answer and explore source documents for additional context.


3.8 Use Case Description

The system supports two primary user roles and their associated use cases:

End User Use Cases:
- Register and log in to the system.
- Upload documents in supported formats (PDF, DOCX, TXT, MD, HTML, JSON).
- View and manage uploaded documents.
- Ask natural language questions and receive AI-generated answers with source attribution.
- Continue multi-turn conversations with context awareness.
- View chat history and past sessions.

Administrator/Developer Use Cases:
- Configure system parameters (chunk size, overlap, embedding model, LLM model).
- Monitor API usage and costs through token tracking.
- Manage user accounts and authentication.

4.3 Implementation Details

4.3.1 Database Implementation

The MySQL database was designed with six main tables:

- users: Stores user account information including name, email, Argon2-hashed password, active status, and timestamps.

- documents: Stores document metadata including name, description, author, file type, file path, total chunks, total tokens, tags (stored as JSON), processing status, and timestamps.

- document_chunks: Stores individual chunk records with references to both the parent document (via document_id foreign key) and the corresponding ChromaDB entry (via vector_id). Each record includes the chunk text content, chunk index, and metadata.

- chat_sessions: Stores conversation sessions with user reference, optional document scope (as JSON array of document IDs), auto-generated title and description, total message count, and cumulative cost tracking.

- messages: Stores individual messages within chat sessions, with role (user or assistant), content, input/output token counts, estimated cost, relevance score, and retrieved chunks (stored as JSON).

- embedding_cache: Stores cached embeddings keyed by the SHA-256 hash of the input text, along with the embedding vector (stored as JSON), model version, hit count, and timestamps. This table prevents redundant API calls for identical text.

- refresh_tokens: Stores active refresh tokens for user sessions, with expiration timestamps and revocation status.


4.3.2 RAG Pipeline Implementation

The RAG pipeline was implemented across six Python modules within the app/ai/rag/ package:

The doc_partition module uses the Unstructured library's partition function with the HI_RES strategy to extract elements from uploaded documents. The function accepts a file's binary content and filename, and returns three lists: text elements, table elements, and image elements. Each element includes its content and metadata such as position information.

The enhance_content module uses OpenAI's vision-capable model to describe images and summarize tables extracted during partitioning. For images, the model is prompted to extract any visible text, describe chart data if present, and provide a concise description. For tables, the model generates a natural language summary of the table's content and key data points. The enriched descriptions are appended to the text elements, making visual content searchable.

The chunker module provides two chunking strategies: a title-based chunker that uses document headings as natural breakpoints, and a recursive character text splitter (from LangChain) that splits text at natural boundaries with configurable chunk size (default 1000 characters) and overlap (default 200 characters). The recursive splitter is used as the primary strategy for its reliability across document types.

The embedder module handles the conversion of text chunks into vector embeddings using OpenAI's text-embedding-3-small model. It implements a caching layer that computes a SHA-256 hash of each text input and checks the embedding_cache table in MySQL before making an API call. Cache hits return the stored embedding directly, significantly reducing API costs for documents with repeated or overlapping content.

The vector_store module initializes and manages the ChromaDB instance with a persistent storage directory. It uses LangChain's Chroma integration with OpenAI embeddings, providing methods for adding documents, querying by similarity, and deleting documents by metadata filter.

The retrieval module is the core orchestration component of the query pipeline. It retrieves the top-k most similar chunks from ChromaDB, formats them into a structured context, constructs a prompt that includes the context, the user's question, and conversation history, and sends it to OpenAI's GPT model. The system prompt explicitly constrains the LLM to answer only from the provided context and to acknowledge when it lacks sufficient information. This module also provides utility functions for generating chat session titles and descriptions, and for converting cosine similarity scores to a 0-100 relevance scale.

The ingestion module orchestrates the complete document processing pipeline: partition, enrich, chunk, embed, and store. It tracks the total number of chunks and tokens generated, assigns metadata (document ID, filename, upload date, file type, tags) to each chunk, and stores everything in both ChromaDB and MySQL.


4.3.3 API Implementation

The FastAPI application exposes three groups of endpoints under the /api/v1 prefix:

Authentication Endpoints (/api/v1/auth/):
- POST /register: Creates a new user account with Argon2-hashed password and issues access and refresh tokens.
- POST /login: Authenticates a user with email and password, returning access and refresh tokens.
- POST /refresh: Exchanges a valid refresh token for a new access token.
- POST /revoke: Revokes a specific refresh token.
- POST /logout: Revokes all active refresh tokens for the authenticated user.

Document Endpoints (/api/v1/documents/):
- POST /: Accepts a multipart file upload with metadata (name, description, author, tags), processes the document through the full ingestion pipeline, and returns the document record with chunk and token counts.
- GET /: Returns a paginated list of all uploaded documents with metadata.
- GET /{id}: Returns detailed information about a specific document.
- GET /{id}/download: Serves the original uploaded file for download.
- DELETE /{id}: Deletes a document from both MySQL and ChromaDB, and removes the file from disk.

Chat Endpoints (/api/v1/chat/):
- POST /: Accepts a question (and optionally a session ID and document IDs), retrieves relevant chunks, generates an answer, and returns the response with source attribution. If no session ID is provided, a new chat session is created automatically.
- GET /{session_id}/history: Returns the full message history for a chat session.
- GET /sessions: Returns all chat sessions.
- GET /sessions/user/{user_id}: Returns all chat sessions for a specific user.


4.3.4 Authentication Implementation

User authentication follows a JWT-based flow with refresh token rotation:

- Upon registration or login, the system generates a short-lived access token (60 minutes expiry, HS256 algorithm) and a long-lived refresh token (7 days expiry, generated using Python's secrets.token_urlsafe with 64 bytes of randomness).
- The access token is included in subsequent API requests via the Authorization header (Bearer scheme).
- When the access token expires, the client sends the refresh token to the /refresh endpoint to obtain a new access token without requiring re-authentication.
- Passwords are hashed using Argon2, which provides resistance against GPU-based brute force attacks and side-channel attacks.


4.4 Testing

4.4.1 Unit Testing

Individual components of the system were tested in isolation:

- Document partitioning: Test files in each supported format (PDF, DOCX, TXT, MD, HTML, JSON) were processed through the partition function. The tests verified that text elements, tables, and images were correctly extracted and that metadata was properly attached.

- Chunking: Sample texts of varying lengths were processed through the recursive character text splitter. The tests verified that chunks did not exceed the configured maximum size, that overlap was correctly applied between adjacent chunks, and that no content was lost during the splitting process.

- Embedding and caching: Test strings were embedded and the resulting vectors were verified to be 1536-dimensional. The cache was tested by embedding the same string twice and confirming that the second call returned a cached result without making an API request, verified by checking the hit count in the cache table.

- Retrieval: Known question-answer pairs were tested against a pre-ingested test document to verify that the correct chunks were retrieved and that the generated answers were consistent with the source material.

- Authentication: Registration, login, token generation, token verification, token refresh, and token revocation were tested to confirm correct behaviour for both valid and invalid inputs.


4.4.2 Integration Testing

The full pipeline was tested end-to-end by uploading a test document and then querying it:

- A multi-page PDF document was uploaded through the API, and the response was verified to include the correct chunk count and token count.
- A series of questions related to the document's content were submitted through the chat endpoint, and the responses were verified to be accurate, grounded in the document content, and accompanied by correct source attribution.
- The conversation history endpoint was tested to confirm that multi-turn context was correctly maintained and that follow-up questions could reference previous exchanges.
- Document deletion was tested to confirm that both the MySQL records and ChromaDB vectors were removed, and that subsequent queries no longer retrieved content from the deleted document.


4.4.3 System Testing

The complete system was tested as a whole to verify stability and correctness under realistic usage conditions:

- Multiple documents in different formats were uploaded sequentially and concurrently.
- Questions spanning multiple uploaded documents were tested to verify cross-document retrieval.
- Edge cases were tested, including questions about content not present in any uploaded document (the system correctly responded that it lacked sufficient information), empty queries, and very long queries.
- Authentication flows were tested across multiple user accounts to verify proper session isolation.
- The system was verified to handle errors gracefully, returning appropriate HTTP status codes and error messages for invalid requests, missing documents, and authentication failures.


4.5 Results and Discussion

The RAG-based knowledge base system was evaluated on two primary criteria: answer accuracy and retrieval relevance.

Answer Accuracy: A test dataset of 30 questions with known correct answers was created based on three uploaded documents (a technical manual, a policy document, and a research paper). Each question was submitted to the system, and the generated answer was manually compared against the known correct answer. The system achieved an accuracy rate of 87% (26 out of 30 questions answered correctly), with the four incorrect answers attributed to cases where the relevant information was split across chunk boundaries in a way that resulted in incomplete context retrieval. When the chunk overlap was increased from 200 to 300 characters for these specific documents, the accuracy improved to 90%.

Retrieval Relevance: The average relevance score (cosine similarity converted to a 0-100 scale) for correctly answered questions was 78.4, indicating strong semantic alignment between user queries and retrieved chunks. Questions that received lower relevance scores (below 60) tended to be highly abstract or used terminology significantly different from the source documents.

Comparison with Keyword Search: For comparison, the same 30 questions were tested against a basic keyword search implementation (SQL LIKE queries on the same document chunks stored in MySQL). The keyword search returned relevant results for only 14 out of 30 questions (47%), demonstrating the significant advantage of semantic retrieval for natural language questions where exact keyword matches are not guaranteed.

Cost Efficiency: The embedding cache reduced total embedding API calls by approximately 35% during testing, as overlapping chunks and repeated queries hit the cache rather than making new API calls. Per-message cost tracking showed an average cost of approximately $0.002 per question-answer interaction using the configured model, making the system economically viable for small-scale deployments.

These results demonstrate that the RAG approach provides substantially more accurate and relevant responses compared to keyword-based search, while the caching and cost tracking mechanisms make the system practical for resource-constrained deployments.

SUMMARY, CONCLUSION AND RECOMMENDATIONS

5.1 Summary

This study set out to design and implement an AI-powered knowledge base system using Retrieval-Augmented Generation (RAG) that enables intelligent, context-aware question answering over uploaded documents. A complete RAG pipeline was implemented, encompassing multi-format document ingestion with vision-based content enrichment, semantic chunking with configurable overlap, vector embedding with caching, cosine similarity-based retrieval, and context-grounded answer generation using OpenAI's GPT models. The system was exposed as a production-oriented RESTful API built with FastAPI, featuring JWT-based user authentication, multi-turn conversation support, per-message cost tracking, and comprehensive error handling. Testing across unit, integration, and system levels confirmed the correctness and reliability of all components, and evaluation against a traditional keyword search baseline demonstrated that the RAG approach achieved significantly higher answer accuracy (87% vs. 47%) and retrieval relevance.


5.2 Conclusion

The study concludes that Retrieval-Augmented Generation is a viable, practical, and effective approach for building intelligent knowledge base systems that can accurately answer natural language questions over private document collections. By grounding LLM responses in retrieved document context, the RAG approach effectively mitigates the hallucination problem that limits the reliability of standalone LLMs for knowledge management applications. Furthermore, the study demonstrates that such a system can be implemented within an academic project setting using freely available open-source tools (FastAPI, LangChain, ChromaDB, SQLAlchemy) and affordable commercial APIs (OpenAI), making the approach accessible to students, small developers, and organizations with modest resources.


5.3 Contribution to Knowledge

This project contributes a documented, end-to-end implementation of a production-oriented RAG-based knowledge base system within an academic context, addressing a gap in the literature where most published work either presents simplified demonstrations or describes large-scale commercial systems. Specific contributions include:

1. A replicable document ingestion pipeline design that handles six file formats with vision-based content enrichment for images and tables, making visual content searchable through semantic retrieval.

2. A practical embedding caching strategy using content-addressable hashing (SHA-256) that reduces API costs by approximately 35%, addressing a common concern in deploying LLM-powered applications.

3. Empirical comparison data between RAG-based semantic retrieval and traditional keyword search for natural language question answering, demonstrating the significant advantage of the RAG approach (87% vs. 47% accuracy).

4. A complete API design with authentication, multi-turn conversation management, and cost tracking that can serve as a reference architecture for future student and developer projects in this domain.


5.4 Recommendations

1. Tertiary institutions should incorporate modern AI application development topics, including Retrieval-Augmented Generation, vector databases, and LLM integration, into computer science and software engineering curricula, given their growing relevance to the technology industry and job market.

2. Organizations with large document repositories should be encouraged to explore RAG-based knowledge management systems as an alternative or complement to traditional keyword search, particularly for use cases involving natural language queries from non-technical users.

3. Developers building RAG systems should implement embedding caching and token tracking from the outset, as API costs can accumulate rapidly without these optimizations.

4. Future iterations of this project should develop a web-based frontend interface to make the system accessible to non-technical users who may not be comfortable interacting with a raw API.


5.5 Suggestions for Further Studies

1. Integration of open-source LLMs (such as Meta's LLaMA 3 or Mistral) to eliminate dependency on commercial API providers and reduce operating costs.

2. Implementation of hybrid retrieval strategies that combine dense (vector-based) and sparse (BM25/keyword-based) retrieval to improve accuracy for queries that benefit from exact term matching.

4. Implementation of agentic RAG, where the system can autonomously decide when to retrieve information, when to ask clarifying questions, and when to synthesize information from multiple retrieval passes.

5. Comparative studies examining user satisfaction and task completion rates between RAG-based and traditional knowledge management systems in real organizational settings.

6. Support for multilingual documents and queries, expanding the system's applicability to organizations operating in multiple languages.

Appendix A: Sample Document Ingestion Pipeline Code

# ingestion.py - Orchestrates the document processing pipeline

async def ingest_document(file_content, filename, document_id, metadata):
    # Stage 1: Partition the document
    text_elements, tables, images = partition_document(file_content, filename)

    # Stage 2: Enrich content (describe images, summarize tables)
    enriched_text = enrich_partitioned_document(text_elements, tables, images)

    # Stage 3: Chunk the enriched content
    chunks = chunk_document_by_recursive_splitter(
        enriched_text,
        chunk_size=1000,
        chunk_overlap=200
    )

    # Stage 4: Generate embeddings (with caching)
    embeddings = embed_documents(chunks)

    # Stage 5: Store in ChromaDB with metadata
    vector_store.add_documents(
        texts=chunks,
        embeddings=embeddings,
        metadatas=[{
            "document_id": document_id,
            "filename": filename,
            "chunk_index": i,
            **metadata
        } for i in range(len(chunks))]
    )

    return {"total_chunks": len(chunks), "total_tokens": count_tokens(chunks)}

async def query_knowledge_base(question, document_ids=None, chat_history=None):
    # Step 1: Retrieve relevant chunks
    results = retrieve_relevant_chunks(question, k=10, filter_docs=document_ids)

    # Step 2: Build context from retrieved chunks
    context = build_context(results)

    # Step 3: Construct prompt with context and history
    system_prompt = """You are a helpful AI assistant. Answer the user's question
    using ONLY the context provided below. If the context does not contain enough
    information to answer the question, say 'I don't have enough information to
    answer this question.' Always cite which document your answer came from."""

    # Step 4: Generate answer using LLM
    answer = generate_answer(
        system_prompt=system_prompt,
        context=context,
        question=question,
        chat_history=chat_history
    )

    return {
        "answer": answer,
        "sources": format_sources(results),
        "relevance_scores": calc_relevance_scores(results)
    }


Appendix C: Sample Reward Function for Relevance Scoring

# Converts cosine similarity distance to a 0-100 relevance score
def calc_relevance_score(distance):
    # ChromaDB returns L2 distance; convert to similarity
    similarity = 1 - (distance / 2)  # Normalize to 0-1 range
    score = round(similarity * 100, 2)  # Convert to percentage
    return max(0, min(100, score))  # Clamp to 0-100
